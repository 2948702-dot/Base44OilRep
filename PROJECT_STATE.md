# SmartOil: текущее состояние

Короткая точка входа для продолжения работы. Полная документация читается только по необходимости.

## Два продуктовых направления

В репозитории развиваются два независимых продукта:

1. **SmartOil** — учёт и предиктивная диагностика масел. Код: `base44/`, `src/pages`, `src/components`.
2. **AI Investigation Platform** («Объяснительная») — платформа внутренних расследований.
   Код: `investigation/`, `src/investigation/`. Документация: `src/docs/investigation/`.

Продукты не пересекаются по данным и сущностям. Работая с одним, не менять схемы другого.

## Текущий фокус SmartOil

- Релиз: стабилизация эксплуатационного контура.
- Следующий приоритет: `KI-001` / P0 — RLS и поддержка полного массива `User.asset_ids`.
- После него: `KI-002` и `KI-003` — acceptance для MaintenanceEvent, OilLifecycle и plan-fact замены масла.

## Текущий фокус AI Investigation Platform

- Стек: PostgreSQL 16 + pgvector, Node 22 + Fastify, Docker на VPS владельца, Caddy,
  деплой через GitHub Actions. Base44 не используется (решение DEC-024, `adr-0002-own-stack.md`).
- Выполнен шаг 0 по §76 ТЗ и переход на собственный стек: ADR, entity model, permissions
  model, схема БД, repository abstractions, file/source subsystem, agent framework,
  Case CRUD, машина стадий, аутентификация, HTTP-контур, развёртывание.
- Реализованы все 18 агентов из §22–§40 ТЗ. Расследование проходит целиком: от свободного описания
  инцидента до выпущенного отчёта, с остановками на утверждении человеком.
- Итоговый отчёт разделяет установленное, заявленное, выведенное и неизвестное;
  факт без ссылки на доказательство и ссылка на неутверждённый вывод отклоняются.
- Работает исполнитель фоновых задач: ответ участника сам запускает извлечение
  утверждений, а в режиме A2 — и весь аналитический цикл до утверждения человеком.
- Работает симулятор расследований и бенчмарк (§51–§52): учебное дело со скрытой истиной,
  Case Director как девятнадцатый агент, четырнадцать метрик качества с защитными
  порогами. Прогон непройден, если отчёт содержит утверждение без опоры, если назван
  непричастный, если версия закрыта преждевременно или исключена верная версия.
- Закрыты шестнадцать дефектов, найденных независимой проверкой кода: контур интервью
  не доходил до участника, граница дела внутри организации не держалась, утверждение
  отправки открывало ссылки в чужих делах, вход не был ограничен по частоте.
- Итоговый отчёт выгружается в DOCX по разделам §40: документ собирается на сервере,
  сохраняет коды выводов рядом с утверждениями и остаётся проверяемым вне системы.
- Проверки зелёные: приёмка §81 — 124/124 на памяти и на PostgreSQL; HTTP-контур — 47/47;
  очередь — 25/25; интерфейс в браузере — 14/14; изоляция и неизменяемость журналов — 8/8;
  бенчмарк учебного дела — защитные метрики пройдены на обоих хранилищах.
- Следующий приоритет: `KI-013` — развернуть на сервере (поддомен, секреты, первый прогон
  Action) и `KI-018` — запустить укрепление доступа готовым Action.
- Рабочее место следователя готово: обзор, хронология, матрица доказательств, карта
  противоречий, доска версий, движение средств, выводы и отчёт — на одной самодостаточной
  странице без внешних запросов.
- Экран участника интервью готов: самодостаточная страница по подписанной ссылке,
  без внешних запросов. Ответ можно дать текстом или голосом; запись расшифровывается
  на том же сервере, участник подтверждает или правит текст, оригинал не меняется.

## Последнее подтверждённое состояние

- Ветка `main` синхронизирована с GitHub.
- Документационный аудит слит PR #1.
- Build и lint проходят.
- Typecheck не проходит из-за накопленного baseline, см. `KI-011`.
- Живой read-only доступ Base44 работает через CLI + Deno.
- Последний production snapshot: 6 активов, 7 агрегатов, 6 проб, 9 результатов анализа.
- SamplingPoint удалён из рабочей модели; legacy-записи production требуют отдельной проверки перед удалением.

- Для входящей пробы без QR `/mobile-lab` должен давать ручной выбор клиента, актива/агрегата или базового масла.

## Инкрементальный старт

1. Найти checkpoint — последний коммит, изменивший этот файл:

   `git log -1 --format=%H -- PROJECT_STATE.md`

2. Посмотреть, что изменилось после checkpoint:

   `git diff --name-status <checkpoint>..HEAD`

3. Если список пуст, прочитать только этот файл и приступить к текущему P0.
4. Если изменения есть, сначала прочитать diff и только документы/модули затронутой области.
5. Полностью читать `ROADMAP.md`, `known-issues.md`, архитектуру и бизнес-правила только при:
   - изменении соответствующего файла;
   - смене продуктового приоритета;
   - противоречии между состоянием, кодом и production;
   - подготовке архитектурного решения или релиза.

## Правило обновления

Обновлять этот файл при изменении:

- текущего приоритета или статуса P0;
- подтверждённого production-состояния;
- незавершённых проверок;
- ключевой архитектуры или источника истины.

Не превращать файл в журнал действий. История остаётся в Git, решения — в `decisions.md`, риски — в `known-issues.md`.
