## 1. Executive summary

**Решение: GO WITH RESTRICTIONS.**

Главный вывод исследования не про Baileys, а про постановку задачи. **Легального способа
читать сообщения из существующей рабочей группы WhatsApp не существует.** Официальный Groups
API от Meta (открыт для всех Official Business Account в 2026) позволяет бизнесу *создавать
и вести собственные* группы до 8 участников. Он не позволяет добавить бизнес-номер в уже
существующую пользовательскую группу и не даёт читать её историю. То есть выбор стоит не
«Baileys или официальный API», а «неофициальный клиент или отказ от проекта».

При этом сама задача — превратить оперативную переписку в структурированную память компании —
поставлена правильно, и Shadow Mode как первый этап выбран верно.

Что делает решение «GO **WITH RESTRICTIONS**»:

1. **Аккаунт расходный.** Использование Baileys нарушает ToS WhatsApp. Бан или разлогин —
   вопрос «когда», а не «если». Значит, архитектура должна считать номер расходным
   материалом, а активом — базу данных. Read-only режим из ТЗ — это самый низкорисковый
   профиль, какой вообще возможен, но не нулевой.
2. **`npm install baileys` сейчас ставит release candidate.** Тег `latest` в npm указывает на
   `7.0.0-rc14` (29.07.2026). Стабильный тег называется `legacy` и указывает на `6.7.24`.
   7.0.0 находится в RC с ноября 2025 — девять месяцев. Версию нужно пинить осознанно.
3. **Правовой аспект в ТЗ не закрыт.** Систематическая запись переписки сотрудников,
   содержащей персональные данные клиентов, с отправкой содержимого во внешние AI API —
   это обработка ПДн (152-ФЗ) и трансграничная передача. Требование «работать преимущественно
   незаметно для сотрудников» здесь конфликтует с законом и с базовым доверием в коллективе.
   Это устранимо одним абзацем уведомления, но устранить нужно **до** запуска, не после.

Технически проект реализуем на VPS с 1 ГБ RAM. Стоимость AI — порядка $15–25/мес на одну
группу при 150 сообщениях в день. Основные риски — не в коде.

## 2. Что выяснено про Baileys

Проверено 16.08.2026 через npm registry, GitHub, документацию и трекер issues.

### Состояние проекта

| Параметр | Значение |
|---|---|
| Репозиторий | `WhiskeySockets/Baileys`, MIT, активно поддерживается |
| npm-пакеты | `baileys` и `@whiskeysockets/baileys` (синхронные версии) |
| dist-tag `latest` | **`7.0.0-rc14`**, опубликован 2026-07-29 |
| dist-tag `legacy` | `6.7.24`, опубликован 2026-07-29 |
| Всего версий | 64 |
| Технология | TypeScript, WebSocket напрямую к серверам WhatsApp, без Chromium |
| Потребление RAM | ~50 МБ на сессию (против 400–500 МБ у whatsapp-web.js с Chromium) |

Хронология 7.x: `rc.7`–`rc.9` в ноябре 2025, затем девятимесячная пауза, затем `rc10`–`rc14`
в мае–июле 2026. Стабильного 7.0.0 на момент исследования нет.

В README проекта висит прямое предупреждение:

> «NOTICE OF BREAKING CHANGE. As of 7.0.0, multiple breaking changes were introduced into the
> library.»

и отдельно:

> «The maintainers of Baileys do not in any way condone the use of this application in
> practices that violate the Terms of Service of WhatsApp.»

### Breaking changes 7.x относительно 6.7.x

- изменился импорт: `makeWASocket` импортируется вместе с `Browsers`;
- **`getMessage` callback стал обязательным** — без него ломаются message retries,
  расшифровка голосований и обработка quoted-сообщений;
- рекомендуемый паттерн обработки событий — `sock.ev.process()` (батчевая обработка) вместо
  подписки на отдельные события;
- переработан механизм LID.

### LID / PN — идентификация отправителя

WhatsApp переводит идентификаторы на LID (скрытые ID вида `1234567890@lid` вместо
`79991234567@s.whatsapp.net`). Для проекта это критично: атрибуция сообщений к сотрудникам —
одно из ядровых требований.

В 7.x есть API: `sock.signalRepository.lidMapping` с методами `getLIDForPN()`,
`getLIDsForPNs()`, `getPNForLID()`, плюс событие `lid-mapping.update`, которое срабатывает,
когда Baileys узнаёт новую пару PN↔LID.

Известные проблемы в трекере (по состоянию на исследование): `getPNForLID()` возвращает
`undefined` даже при доступном `lidMapping`; событие `lid-mapping.update` в ряде случаев не
срабатывает; в call-событиях LID приходит без возможности резолва в номер. Есть отдельный
discussion-тред «LID Mapping Best Practices & Debugging Guide for Production» — то есть тема
живая и не закрытая.

**Вывод по идентификации:** нельзя полагаться только на LID-резолв. Нужен собственный слой
сопоставления (см. раздел 6, таблица `identities`), который накапливает пары PN↔LID↔pushName
по мере их появления и умеет работать при неполных данных.

### Auth state

Мейнтейнеры прямо не рекомендуют `useMultiFileAuthState` для production: он хранит signal-ключи
в JSON-файлах, что приводит к повреждённым сессиям, растущей нагрузке на CPU/IO и рискам
безопасности. Рекомендация — писать собственную реализацию auth state поверх SQL или NoSQL БД.
Интуиция владельца здесь полностью подтверждается.

### История и потеря сообщений

Событие `messages.upsert` приходит с полем `type`:

- `notify` — новое сообщение, полученное при онлайн-соединении;
- `append` — всё остальное: история, backfill, досинхронизация.

В `connection.update` есть флаг, показывающий, что устройство получило все ожидающие
уведомления, накопившиеся за время оффлайна. Гарантий полноты истории при этом нет —
дедупликация и детекция разрывов обязательны на нашей стороне.

### Альтернативы

| Вариант | Оценка |
|---|---|
| **whatsapp-web.js** | Chromium + Puppeteer, 400–500 МБ RAM на сессию, известные утечки памяти при долгих сессиях. На 1 ГБ VPS нежизнеспособен. **Отклонён.** |
| **Evolution API** | REST-обёртка над тем же Baileys. Добавляет удобство и вебхуки, но и слой абстракции, лишний Postgres/Redis, чужой релизный цикл. Риски Baileys наследует полностью. Для одной группы — избыточен. **Отклонён на этапе 1**, может пригодиться при масштабировании на многие аккаунты. |
| **Meta Groups API** | Только группы, созданные бизнесом, до 8 участников; не позволяет войти в существующую группу сотрудников. **Задачу не решает.** |

**Baileys 7.0.0-rc14 остаётся лучшим выбором** — при условии, что PoC подтвердит корректный
резолв идентификаторов на реальной группе.

## 3. Риски — от главных к второстепенным

### R1. Правовой и этический (критический, недооценён в ТЗ)

В рабочих группах есть телефоны и фамилии клиентов, суммы, документы. Система будет их
систематически хранить и отправлять во внешние AI-API за пределы РФ. Это обработка
персональных данных и трансграничная передача. Отдельно: скрытая запись переписки сотрудников
без уведомления — трудовой и репутационный риск, который сработает ровно в тот момент, когда
кто-то узнает.

Пункт ТЗ «работать преимущественно незаметно для сотрудников» я читаю как «не менять привычный
UX», а не «скрыть факт наличия системы» — и предлагаю трактовать именно так.

**Митигация (обязательна до Shadow Mode):**
- одно сообщение в группу: в чате работает служебный аккаунт, он сохраняет переписку для
  внутреннего учёта, отвечать он не будет;
- письменное уведомление сотрудников;
- политика хранения и удаления (раздел 9);
- псевдонимизация клиентских телефонов перед отправкой в LLM (замена на `<PHONE_7>` с
  локальным словарём) — снимает большую часть трансграничного риска почти без потери качества.

### R2. Бан или разлогин служебного аккаунта (высокий, неустранимый)

Baileys выдаёт себя за companion device. Антифрод WhatsApp учитывает низкий процент ответов,
роботизированный тайминг, трафик из датацентровых диапазонов IP. Сообщения без ответа за 48
часов учитываются накопительно в скользящем окне 30 дней. Оценки сообщества по времени жизни
таких аккаунтов расходятся от нескольких недель до многих месяцев.

Read-only профиль убирает большую часть триггеров: нет исходящих сообщений, нет добавления
участников, нет массовой рассылки. Но остаётся датацентровый IP и сам факт нестандартного
клиента.

**Митигация:**
- номер расходный, никогда не личный номер владельца;
- «отлежать» номер: активировать на обычном телефоне, дать ему естественную историю пару
  недель, только потом линковать;
- ноль исходящей активности в первой фазе, включая read receipts и presence updates;
- **актив — это база данных, а не номер.** Потеря аккаунта = re-pairing, а не потеря проекта;
- готовый runbook re-pairing и алерт администратору при `loggedOut`.

### R3. Release candidate в проде (высокий, управляемый)

`latest` = RC, стабильная ветка помечена `legacy`. При этом 6.7.x всё хуже справляется с
LID-миграцией WhatsApp, а идентификация сотрудников — ядро проекта.

**Митигация:** пинить `7.0.0-rc14` точной версией без `^`, запретить автообновление, держать
`6.7.24` как проверенный откат, обновляться только после прогона регрессионного набора.

### R4. Смена протокола WhatsApp (средний, неустранимый)

WhatsApp может изменить протокол в любой момент; SLA нет. Симптом — сообщения перестали
приходить при живом соединении.

**Митигация:** мониторинг `last_whatsapp_event_at` (раздел 9), алерт при аномальной тишине,
принцип RAW FIRST — сырое событие сохраняется до всякого разбора.

### R5. Разрывы в потоке сообщений (средний)

`append` vs `notify`, неполный history sync, downtime сервера.

**Митигация:** идемпотентный INSERT по `(chat_jid, whatsapp_message_id, from_me)`; таблица
`ingest_gaps` с фиксацией периодов недоступности; ежедневная сверка количества сообщений.

### R6. 1 ГБ RAM (средний, измеримый)

Тесно, но реально: Baileys ~50 МБ + Node runtime ~40 МБ + AI worker ~80 МБ + PostgreSQL
~120 МБ + AmneziaWG + ОС. Без Redis, без Chromium, без Docker-оверхеда на каждый сервис.
Точная цифра — после PoC.

### R7. Качество AI-разбора (средний)

Разговорный русский, коллизии алиасов («Муза» / «музыка» / «музыкальная колонка»), сленг,
опечатки, голос. Precision/recall неизвестны до реальных данных — ровно поэтому в ТЗ
правильно заложен этап Evaluation.

### R8. Стоимость (низкий, но растущий)

При 150 сообщениях в день — порядка $15–25/мес. При десяти группах и активной транскрипции —
уже сотни долларов. Нужен учёт токенов с первого дня (раздел 11).

### R9. Диск 20 ГБ (низкий, предсказуемый)

Медиа переполнит диск за месяцы. Решается retention-политикой и выносом медиа (раздел 8).

**Прямого доступа к VPS у меня нет и в этой сессии быть не может.** Сессия работает в
изолированном облачном контейнере, привязанном к GitHub-репозиторию; SSH до сервера владельца

### Предварительная оценка

| Ресурс | Оценка | Комментарий |
|---|---|---|
| CPU | достаточно | Baileys — это разбор WebSocket-фреймов, не расчёты. STT и LLM — внешние API. |
| RAM 1 ГБ | **на грани, вероятно хватит** | Только при дисциплине: без Redis, без Chromium, PostgreSQL с урезанным `shared_buffers`, медиа стримить на диск, а не держать в памяти. Обязателен swap 2 ГБ. |
| Диск 20 ГБ | хватит для этапа 1 | Текст растёт медленно (~50 МБ/год на группу). Медиа — ограничить retention. |
| Amnezia | **не трогать** | Проект не занимает порты 80/443 наружу; Admin API слушает только `127.0.0.1`. Конфликтов быть не должно. |

**Рекомендация: не увеличивать VPS сейчас.** Прогнать PoC, снять реальные цифры RSS под
нагрузкой, и только потом решать. Если после PoC пиковое потребление превысит ~750 МБ — брать
2 ГБ. 4 ГБ на этом этапе точно избыточны.

## 5. Архитектура MVP

```
                      WhatsApp (рабочая группа)
                               │
                    служебный аккаунт «Regatta AI»
                       linked device, READ ONLY
                               │
                          Baileys WS
                               │
╔══════════════════════════════▼════════════════════════════════════╗
║  ПРОЦЕСС 1 — GATEWAY  (Node, ~90 МБ, никогда не должен падать)    ║
║                                                                    ║
║   ev.process() ──► whitelist групп ──► INSERT raw_events           ║
║                                        (идемпотентно, без разбора) ║
║   heartbeat в БД каждые 30 с                                       ║
║   reconnect с backoff                                              ║
╚══════════════════════════════╤════════════════════════════════════╝
                               │ единственный контракт — таблица
                               ▼
                    ┌──────────────────────┐
                    │     PostgreSQL       │  ◄── источник истины
                    │  raw_events (queue)  │      и очередь одновременно
                    │  messages            │      (SKIP LOCKED)
                    │  media / events /... │
                    └──────────┬───────────┘
                               │
╔══════════════════════════════▼════════════════════════════════════╗
║  ПРОЦЕСС 2 — WORKER  (Node, ~120 МБ, падать не страшно)           ║
║                                                                    ║
║   normalize → media download → STT → classify → extract → link     ║
║   Admin API на 127.0.0.1:8080                                      ║
╚══════════════════════════════╤════════════════════════════════════╝
                               ▼
              внешние API: STT, LLM, объектное хранилище
```

### Ключевые архитектурные решения

**Два процесса, а не один и не пять.** ТЗ допускает объединить всё в один процесс ради
экономии RAM. Не стоит: OOM или необработанное исключение в AI-воркере не должно ронять
ingestion. Разделение стоит ~90 МБ и покупает главное свойство системы — «лучше сохранить
сообщение без анализа, чем потерять сообщение». Единственный контракт между процессами —
таблица в PostgreSQL, никакого IPC.

**Redis не нужен.** При 150 сообщениях в день очередь на PostgreSQL с
`SELECT ... FOR UPDATE SKIP LOCKED` полностью достаточна и экономит ~50 МБ RAM, один
контейнер, отдельный backup и отдельную поверхность атаки. Redis имеет смысл вводить, если
пойдут десятки групп и параллельная транскрипция станет узким местом.

**Docker — только для PostgreSQL, или вообще без Docker.** На 1 ГБ оверхед Docker-демона
(~50–80 МБ) заметен. Вариант: PostgreSQL из системного пакета, два Node-процесса под systemd
с `Restart=always` и `MemoryMax`. Проще, легче, лучше диагностируется. Docker-compose добавить
позже, если понадобится воспроизводимость окружения.

**Auth state в PostgreSQL, не в файлах.** Собственная реализация `AuthenticationState`:
`creds` одной строкой, signal-ключи — key-value таблицей. Даёт атомарность, попадание в
backup и отсутствие деградации от разрастания файлов.

## 6. База данных

Тринадцать таблиц. Слои разделены жёстко: сырое → нормализованное → интерпретация.

### Слой 1 — сырьё (никогда не изменяется)

**`raw_events`** — всё, что пришло от Baileys, до всякого разбора. Одновременно очередь.
`id`, `received_at`, `event_type`, `payload jsonb`, `chat_jid`, `wa_message_id`,
`process_status` (`pending`/`done`/`failed`), `attempts`, `last_error`.
Уникальный индекс `(chat_jid, wa_message_id, event_type)` — идемпотентность.

**`ingest_gaps`** — периоды, когда gateway был недоступен. `started_at`, `ended_at`, `reason`.
Отвечает на вопрос «за этот интервал данным можно доверять?».

### Слой 2 — нормализованные данные

**`messages`** — состав по ТЗ, скорректированный под реальные поля Baileys. Убраны поля,
которых Baileys не даёт надёжно; добавлены `sender_push_name`, `is_ephemeral`,
`raw_event_id` (ссылка на источник), `analysis_status`
(`pending`/`skipped`/`analyzed`/`failed`).
Уникальный ключ дедупликации: `(chat_jid, wa_message_id, from_me)`.

**`message_edits`**, **`message_reactions`** — отдельными таблицами, а не полями: правки и
реакции приходят отдельными событиями и должны иметь собственную историю.

**`media`** — `message_id`, `media_type`, `mime_type`, `file_name`, `size_bytes`, `duration_s`,
`sha256`, `storage_backend`, `storage_path`, `download_status`, `downloaded_at`, `expires_at`.

**`transcriptions`** — `media_id`, `text`, `provider`, `model`, `language`, `confidence`,
`duration_ms`, `cost_usd`, `created_at`.

### Слой 3 — справочники

**`employees`** — по ТЗ.
**`identities`** — критично для LID: `employee_id`, `identity_type` (`pn`/`lid`/`push_name`),
`identity_value`, `confidence`, `first_seen_at`, `last_seen_at`. Один сотрудник — много
идентичностей. Именно эта таблица закрывает нестабильность LID-резолва в Baileys.
**`assets`** — суда: `name`, `type`, `active`, `notes`.
**`asset_aliases`** — `asset_id`, `alias`, `alias_normalized` (нижний регистр + лемма),
`is_ambiguous`. Флаг неоднозначности нужен для случаев вроде «Муза» / «музыка».

### Слой 4 — интерпретация

**`events`** — `event_type`, `asset_id`, `component`, `title`, `description`, `status`,
`responsible_employee_id`, `deadline_text`, `deadline_resolved_at`, `confidence`,
`needs_review`, `opened_at`, `closed_at`.

**`event_sources`** — `event_id`, `message_id`, `role`
(`created_from`/`updated_from`/`closed_from`/`context`). Обеспечивает auditability: на любой
вопрос «почему система так решила» отвечает выборка исходных сообщений.

**`event_history`** — `event_id`, `from_status`, `to_status`, `changed_by_message_id`,
`changed_at`, `note`. История не перезаписывается никогда.

**`ai_runs`** — `job_type`, `provider`, `model`, `prompt_version`, `input_tokens`,
`output_tokens`, `cost_usd`, `latency_ms`, `success`, `error`, `created_at`. Учёт стоимости
и воспроизводимость результатов.

## 7. AI pipeline

Каскад с фильтрацией: дорогая модель видит только то, что того стоит.

```
messages (analysis_status = pending)
        │
        ▼
  ЭТАП 0 — правила (0 токенов, ~90% отсева на служебном шуме)
    пусто / стикер / «ок» / «+» / «спасибо» / «👍»
        │ прошло
        ▼
  ЭТАП 1 — окно 10 минут
    сгруппировать подряд идущие сообщения группы в один батч
        │
        ▼
  ЭТАП 2 — классификатор (дешёвая модель, Haiku-класс)
    «есть ли здесь операционное событие?» → yes/no + подсказка типа
        │ yes
        ▼
  ЭТАП 3 — извлечение (Sonnet-класс)
    контекст: батч + quoted + последние N сообщений + открытые события
              по упомянутым объектам + справочники assets/employees
    выход: структурированное событие + confidence + отсылки на message_id
        │
        ▼
  ЭТАП 4 — линковка
    сначала детерминированно: (asset_id, component, status=open, ≤72 ч) → кандидаты
    и только при неоднозначности — обращение к LLM
        │
        ▼
  events + event_sources + event_history
```

Голосовые сообщения входят в конвейер после транскрипции, на этапе 0, как обычный текст.

**Контекст.** Стартовое значение: 30 последних сообщений группы. Настраивается, подбирается
экспериментально на этапе Evaluation. Вся история группы в LLM не отправляется никогда.

**Кэширование промпта.** Справочники (сотрудники, суда, алиасы) и системная инструкция —
статичный префикс на каждом вызове. Prompt caching даёт на нём порядка десятикратной экономии.
Требование: динамические части (текущее время, ID запроса) размещать строго после статичного
префикса, иначе кэш не сработает вообще.

**Псевдонимизация.** Перед отправкой в LLM телефоны клиентов и, при необходимости, фамилии
заменяются на плейсхолдеры с локальным словарём обратного соответствия. Качество извлечения
событий это почти не затрагивает, а юридический профиль улучшает существенно.

**Confidence и пороги (стартовые, уточняются после Evaluation):**

| Порог | Действие |
|---|---|
| ≥ 0.85 | создать событие автоматически |
| 0.60–0.85 | создать с `needs_review = true` |
| < 0.60 | сохранить гипотезу, событие не создавать |

**Версионирование промптов.** `prompts/<job>/v<N>.md` в Git; каждая запись `ai_runs` хранит
`prompt_version`. Иначе через полгода невозможно объяснить расхождение результатов.

**Отрицания и исправления** («не Муза, а Сансара», «отбой», «я ошибся») обрабатываются как
обычное извлечение с явной инструкцией на коррекцию: событие получает новую запись в
`event_history`, старая версия сохраняется.

## 8. Хранение медиа

Оценка вариантов из ТЗ:

| Вариант | Оценка |
|---|---|
| A. Локально | Просто, быстро, ноль зависимостей. Ограничение — 20 ГБ на всё. |
| B. Google Drive | Есть подводный камень: service account **не имеет собственной квоты** и не может владеть файлами в личном My Drive — для этого нужен Shared Drive, доступный только в Google Workspace. У аккаунта `@gmail.com` Shared Drive нет. Значит, потребуется OAuth refresh-token от личного аккаунта: он протухает, требует ручного перевыпуска и ломает работу без предупреждения. Для машинного пайплайна — плохой выбор. |
| C. S3-совместимое | Правильный вариант для машины: статические ключи, не протухают, дёшево, presigned URL, стандартный SDK. |
| D. Гибрид | Рекомендуется. |

**Рекомендация — гибрид с фазами:**

- **Этап 1:** только локально, `/var/lib/regatta/media/YYYY/MM/DD/<sha256>.<ext>`,
  в PostgreSQL — только метаданные и путь. Мониторинг заполнения диска, retention 90 дней.
- **Этап 2:** S3-совместимое хранилище как основной backend, локально — только временный буфер
  на время скачивания. `storage_backend` в таблице `media` заложен под это с самого начала.
- **Google Drive:** только как человекочитаемый архив выгрузок для владельца, не как хранилище
  пайплайна.

**Дедупликация по `sha256`** — одно и то же фото, пересланное трижды, хранится один раз.

**Порядок скачивания.** Media-ключи WhatsApp живут ограниченное время. Скачивание ставится в
очередь немедленно при получении сообщения, с ретраями и exponential backoff, и не блокирует
ingestion.

| 1 | PostgreSQL слушает только `127.0.0.1`, наружу не публикуется | обязательно |

## 10. PoC — минимальный первый тест

Цель этапа 2: за один-два вечера получить ответ «работает / не работает», не построив при этом
половину системы.

**Что делает PoC:** один файл, ~150 строк. Подключается к Baileys `7.0.0-rc14`, пишет auth
state в SQLite (не PostgreSQL — на этом этапе не важно), слушает одну тестовую группу,
складывает каждое событие в SQLite как есть и печатает разобранное summary в консоль.

**Чего PoC не делает:** ни PostgreSQL, ни AI, ни очередей, ни Docker, ни Admin API.

**Проверочный лист** (тестовая группа, три участника, два телефона плюс служебный номер):

| # | Проверка | Критерий прохождения |
|---|---|---|
| 1 | Pairing code без QR | сессия поднимается |
| 2 | Русский текст, эмодзи | без искажений |
| 3 | **`sender_jid` резолвится в номер телефона** | **ключевая проверка. Если LID не резолвится ни через `lidMapping`, ни через `pushName` — это блокер** |
| 4 | Reply / quoted | `quoted_message_id` присутствует |
| 5 | Упоминание `@` | mentions извлекаются |
| 6 | Фото + подпись | скачивается, caption на месте |
| 7 | Голосовое 30 с | скачивается, `.ogg` воспроизводится |
| 8 | PDF | скачивается, имя файла верное |
| 9 | Правка сообщения | приходит событие правки |
| 10 | Удаление сообщения | приходит событие удаления |
| 11 | `kill -9` процесса, рестарт | сессия восстанавливается **без нового pairing** |
| 12 | Отключить сеть на 10 мин, послать 5 сообщений, вернуть | все 5 доезжают, `type` фиксируется |
| 13 | Дедупликация после history sync | дублей нет |
| 14 | RSS процесса через 24 ч | стабилен, без утечки |
| 15 | Аккаунт жив через 72 ч в read-only | не разлогинен |

**Пункт 3 — точка принятия решения.** Не проходит на rc14 → повторить на `6.7.24`. Не проходит
на обеих → возвращаемся к архитектуре с обязательной ручной привязкой сотрудников по
`pushName`, и это меняет оценку трудозатрат.

Параллельно с PoC: заказать SIM, активировать номер на обычном телефоне, дать ему отлежаться.

## 11. Ресурсы и стоимость

### RAM (оценка, требует подтверждения на PoC)

| Компонент | Idle | Пик |
|---|---|---|
| Gateway (Node + Baileys) | 85 МБ | 130 МБ |
| Worker (Node + AI) | 110 МБ | 190 МБ |
| PostgreSQL (`shared_buffers=96MB`) | 130 МБ | 190 МБ |
| ОС + AmneziaWG | 180 МБ | 220 МБ |
| **Итого** | **~505 МБ** | **~730 МБ** |

При 1024 МБ остаётся ~290 МБ запаса в пике. Тесно, но рабоче — при условии swap 2 ГБ и
`MemoryMax` в systemd-юнитах. **Решение об апгрейде — только после измерений на PoC.**

### Диск

| Данные | Год |
|---|---|
| Текст + JSONB (1 группа, 150 сообщ./день) | ~1,2 ГБ |
| Медиа (~25 файлов/день, retention 90 дней) | ~8 ГБ единовременно |
| PostgreSQL WAL + индексы | ~1 ГБ |

Помещается в 20 ГБ при работающей retention-политике.

### Стоимость AI

Допущения: 1 группа, 150 сообщений/день, 20 голосовых по ~30 с. Цены Anthropic на 16.08.2026.

| Стадия | Модель | Расчёт | В месяц |
|---|---|---|---|
| Транскрипция | внешний STT | ~10 мин/день × ~$0.006/мин | ~$2 |
| Классификация | Haiku 4.5 ($1 / $5 за 1M) | ~48k in + 9k out в день | ~$3 |
| Извлечение событий | Sonnet 5 ($3 / $15 за 1M) | ~100k in + 15k out в день, с prompt caching | ~$10 |
| Линковка + сводка | Haiku 4.5 | небольшой объём | ~$2 |
| **Итого** | | | **~$17/мес** |

Границы диапазона: если весь разбор гнать через Haiku 4.5 — порядка **$6/мес**; если через
Opus 5 ($5 / $25 за 1M) — порядка **$45/мес**. Prompt caching на статичном префиксе
(справочники + инструкция) даёт кратную экономию и должен быть включён с первого дня.

Стоимость масштабируется примерно линейно по числу групп. Учёт по факту — таблица `ai_runs`.
