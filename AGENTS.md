# AGENTS.md

Инструкции для AI-агентов (Codex, Claude и др.), работающих с этим репозиторием.

## О проекте

SmartOil — система предиктивной диагностики масел и оборудования. Учёт проб масел, контроль состояния узлов, анализ трендов, рекомендации по ТО.

**Стек:**
- Frontend: React (JSX), Tailwind, shadcn/ui
- Backend: Base44 serverless functions (Deno), entry.ts на TypeScript
- Сущности: JSON-схемы в `base44/entities/*.jsonc`

**Иерархия данных:**
Client → Asset → EquipmentUnit → OilSample

**Источники истины:**
- Моточасы агрегата: `MaintenanceEvent` → `EquipmentUnit.current_*`
- Масло агрегата: `EquipmentUnit.current_oil_type_id`
- Пороги: custom thresholds агрегата → `ThresholdRule` выбранного масла
- Отдельной сущности `SamplingPoint` нет: один `EquipmentUnit` является единственным местом отбора.
- QR и способ отбора хранятся в `EquipmentUnit.sampling_qr_code` и `EquipmentUnit.sampling_method`.

**Франчайзи и роли:**
- `admin` — глобальный администратор платформы SmartOil.
- `client_admin` — администратор франчайзи/клиента, scoped через `client_id`; не равен глобальному `admin`, но включает права лаборанта и мобильного оператора в своей области.
- `lab_technician` — лаборант франчайзи/клиента, scoped через `client_id`.
- `/mobile-lab` доступен `admin`, `client_admin` и `lab_technician`.
- `superintendent` и `captain` не вводят лабораторные анализы; они видят данные в своей области доступа.
- Прямой доступ к управлению пользователями для `client_admin` не открывать без отдельной backend-функции scoped-приглашений.

## Обязательный старт каждой сессии

При открытии нового потока или продолжении работы после паузы агент обязан самостоятельно восстановить контекст проекта. Пользователь не должен повторно просить «продолжай по ROADMAP».

Порядок действий:

1. Проверить текущую ветку и `git status`.
2. Прочитать только `PROJECT_STATE.md`.
3. Получить checkpoint командой `git log -1 --format=%H -- PROJECT_STATE.md`.
4. Посмотреть `git diff --name-status <checkpoint>..HEAD`.
5. Если после checkpoint ничего не изменилось, не перечитывать остальные документы.
6. Если изменения есть, читать только diff и документы/модули затронутой области.
7. Полностью открывать `ROADMAP.md`, `known-issues.md`, `decisions.md` и бизнес-правила только при их изменении, смене приоритета, противоречии или архитектурной задаче.
8. Если пользователь не задал другую конкретную задачу или приоритет, начать с P0 из `PROJECT_STATE.md`.
9. Не считать документацию автоматически истинной, если код или production ей противоречат: зафиксировать расхождение и работать от подтверждённого состояния.
10. После значимого этапа обновить `PROJECT_STATE.md` и только действительно затронутые долгосрочные документы.

Явная текущая команда пользователя всегда имеет приоритет над автоматическим порядком.

### Экономия контекста и времени

- Сначала использовать `git diff --stat`, `git diff --name-only` и `rg`; полный diff читать только для релевантных файлов.
- Не перечитывать файлы, которые не менялись после checkpoint и не относятся к задаче.
- Не повторять build/lint/production-проверку, если результат уже подтверждён после последнего изменения связанных файлов; перед финальным коммитом build и lint остаются обязательными.
- Production-запросы ограничивать фильтрами, нужными сущностями и полями.
- Большие независимые чтения и проверки запускать параллельно.
- В отчёте фиксировать результат, риск и следующий шаг, а не хронологию всех команд.

## КРИТИЧНО: работа с русским текстом

Многие файлы содержат русский текст в строках UI. PowerShell в Windows по умолчанию использует консольную кодировку CP866, что приводит к mojibake при чтении файлов через `Get-Content` и срывает патчи через `str_replace`.

**Правила:**

1. Перед PowerShell-командой с русским текстом — выполнять `chcp 65001 | Out-Null`.
2. Для чтения файлов с русским текстом — НЕ использовать `Get-Content` или `cat`. Использовать встроенный инструмент чтения файлов агента.
3. Для поиска по русским строкам — `Select-String -Encoding utf8` или встроенный поиск агента.
4. Для `str_replace` по русским строкам — `old_str` формировать только из нативного чтения, не из вывода PowerShell.
5. Если патч на якоре с русским текстом не цепляется — НЕ угадывать другой якорь. Перечитать файл правильным способом.

## Архитектурные ограничения Base44

1. **Импорт shared-модулей между serverless-функциями не поддерживается.** Каждая функция деплоится как изолированный модуль. Локальные импорты через `../shared/...` не работают.

2. **Function-to-function вызовы** через `base44.functions.invoke()` поддерживаются (подтверждено spike-тестом для роли admin). Для других ролей требуется отдельная проверка перед использованием.

3. **Версия SDK хардкодится** во всех функциях: `npm:@base44/sdk@0.8.25`. Не менять без согласования.

## Живые проверки Base44

Перед выводами о production-данных агент должен проверить их через один из двух независимых каналов:

1. Base44-плагин Codex.
2. Авторизованный Base44 CLI + Deno через `base44 exec`.

Если плагин возвращает `token_expired`, не считать CLI также неработающим: это разные OAuth-сессии. Использовать CLI как резервный read-only канал по инструкции `src/docs/base44-live-access.md`.

Перед `base44 exec` обязательно:

- выполнить `base44 whoami`;
- проверить `base44/.app.jsonc`;
- начинать с операций чтения;
- не выполнять `create`, `update` или `delete` без прямого запроса владельца.

На Windows использовать локальный npm-кэш проекта: `--cache .npm-cache`.

## Визуальная проверка UI

Если in-app Browser недоступен или не видит нужную страницу, использовать резервный Playwright CLI-путь:

1. Собрать проект обычной командой `npm run build`.
2. Если `npm run dev` или `vite preview` падают в Codex sandbox с `Access is denied` / `Could not resolve vite.config.js`, поднять временный static server для папки `dist` с SPA fallback.
3. Запускать Playwright CLI через `npx --yes --cache .npm-cache --package @playwright/cli playwright-cli`.
4. На Windows для Playwright задавать workspace-local окружение:
   - `LOCALAPPDATA=<repo>/.localappdata-<runId>`
   - `PLAYWRIGHT_BROWSERS_PATH=<repo>/.playwright-browsers`
5. Использовать уникальное имя сессии `-s=<project>-<runId>`, чтобы не конфликтовать с зависшими daemon-файлами.
6. Проверять мобильный viewport через `resize 390 844`, затем делать `snapshot` и при необходимости `screenshot --filename output/playwright/<name>.png`.
7. После проверки закрыть сессию, остановить временный сервер и удалить `.localappdata-*`, `.playwright-cli`, `.playwright-browsers`, `output`.

Полный рецепт и причины обходного пути: `src/docs/engineering-practices.md`.

## Сохранение форм — обязательный паттерн

Все формы, выполняющие `update`/`create` сущностей Base44, ДОЛЖНЫ использовать:

1. **`buildPayload`** из `src/utils/payload.js` — для очистки payload от запрещённых системных полей.
2. **`useSaveMutation`** из `src/hooks/useSaveMutation.jsx` — для отображения ошибок сохранения.

**Запрещено:**
- Передавать `form` или `data` напрямую в `entity.update()` или `entity.create()`.
- Использовать сырой `useMutation` без `errorBlock` для сохранения форм.

**Пример:**
См. `src/pages/AssetDetail.jsx` (функция `save`).

### Композитные формы (несколько сущностей в одном диалоге)

Если форма редактирует несколько сущностей одновременно (например, `OilReference` + `ThresholdRule`), используется паттерн:

1. Дочерний компонент экспортирует `saveAll()` через `forwardRef` + `useImperativeHandle`.
2. Родительская мутация сохраняет свою сущность первой, затем вызывает `childRef.current.saveAll()`.
3. Ошибки дочернего сохранения превращаются в `throw new Error(...)`, чтобы `useSaveMutation` показал их через `errorBlock`.

**Пример:** `OilFormDialog.jsx` + `OilThresholdsEditor.jsx`.

### Snapshot-поля и ручное редактирование

Некоторые snapshot-поля (например, `EquipmentUnit.current_oil_type_id`) могут заполняться **двумя путями**:
1. Серверной функцией пересчёта (при создании MaintenanceEvent "смена масла")
2. Фронтом при ручном редактировании справочника агрегата

Для сценария (2) фронт должен **явно** синхронизировать snapshot с источником в payload:

```javascript
const dataWithSync = {
  ...d,
  current_oil_type_id: d.oil_type_id || null,
};
const payload = buildPayload(dataWithSync, FIELDS, NUMBER_FIELDS);
```

Это нужно, потому что серверная функция при пересчёте даёт приоритет snapshot-значению — без явной синхронизации она "проглотит" изменение фронта.

**Где это применяется сегодня:** `EquipmentUnits.jsx`, `AssetDetail.jsx`, `Assets.jsx` — синхронизация `oil_type_id` ↔ `current_oil_type_id`.

**Список форбидден-полей** (никогда не отправляются в payload):
`id`, `created_date`, `updated_date`, `created_by`, `updated_by`, а также поля с префиксом `current_*`, кроме явно документированных исключений вроде `EquipmentUnit.current_oil_type_id`.

### Ветки и pull request

По умолчанию существенные изменения выполнять не напрямую в `main`, а в отдельной ветке `codex/<short-task-name>` с последующим push и draft PR.

К существенным изменениям относятся:

- бизнес-логика, роли, RLS и backend-функции;
- схемы Base44, миграции и production-данные;
- формы сохранения, дашборды, мобильные сценарии и пользовательские потоки;
- изменения, затрагивающие несколько файлов или требующие ручной приёмки.

Прямой коммит в `main` допустим только для низкорисковых правок: документация, мелкий текст, очевидный однострочный фикс или служебная фиксация практик. Если есть сомнение — создать ветку.

Перед началом существенной задачи:

1. Проверить `git status`.
2. Если рабочее дерево чистое и текущая ветка `main`, создать ветку `codex/<short-task-name>`.
3. Не смешивать в одном PR несвязанные изменения.
4. После build/lint/проверок сделать коммит, push и draft PR.
5. В финальном отчёте дать ссылку на PR и явно указать, что нужно принять вручную.

## Открытые вопросы

### Скрытые в UI поля OilReference

Следующие 7 паспортных параметров присутствуют в схеме `OilReference.jsonc`, но скрыты из всех форм UI и whitelist'ов (`OIL_REFERENCE_FIELDS`):

- `passport_viscosity_100`
- `passport_viscosity_index`
- `passport_flash_point`
- `passport_pour_point`
- `passport_tbn`
- `passport_tan`
- `passport_ash_content`

**Причина:** продукт SmartOil построен вокруг собственной лаборатории, которая измеряет 6 параметров (вязкость 40°C, плотность, диэлектрика, вода ppm, активность воды, железо мг/л). Эти 7 паспортных параметров не используются ни в расчётах, ни в порогах, ни в отчётах.

**Что делать при добавлении новых типов диагностики** (через 6+ месяцев — например, частицы по фракциям): добавлять новые поля, не возвращая скрытые. Это разная физика измерений.

**Если поле нужно восстановить:** добавить обратно в `OIL_REFERENCE_FIELDS` и `OIL_REFERENCE_NUMBER_FIELDS`, в форму `OilFormDialog.jsx`, при необходимости — в таблицу `OilReferenceDB.jsx`. Схема Base44 этого не требует — поля там есть.

### SamplingSchedule: поведение серверного пересчёта при ручной установке

В форме `SamplingSchedules.jsx` суперинтендант может вручную устанавливать `next_sample_due_date`, `next_sample_due_hours`, `current_stage`, `samples_in_current_stage`. По решению продукта:
- Капитан / механизатор НЕ имеет доступа к этой форме (защита через RLS).
- Если требуется сдвинуть конкретную пробу — это эскалируется на суперинтенданта.

Открытый вопрос для будущей серверной задачи: что должна делать серверная функция при создании новой `OilSample`, если суперинтендант ранее вручную установил `next_sample_due_*`?

Возможные варианты:
- (a) Всегда пересчитывать по расчёту графика — ручное значение всегда перетирается следующей пробой.
- (b) Не трогать ручное значение, пока оно не пустое — суперинтендант сам должен сбросить.
- (c) Использовать ручное значение один раз для следующей пробы, потом возвращаться к автомату.

Предлагаемое решение: вариант (c). Требует подтверждения перед реализацией серверной функции пересчёта графика.
