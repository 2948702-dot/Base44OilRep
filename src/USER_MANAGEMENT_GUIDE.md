# Пользователи, роли и область доступа

## Модель ролей

### Администратор (`admin`)

- видит всех клиентов и все данные;
- управляет пользователями и справочниками;
- выполняет административные миграции и коррекции;
- отвечает за публикацию и эксплуатационную приемку.

### Администратор клиента / франчайзи (`client_admin`)

- привязан к одному `client_id`;
- видит данные только своего клиента;
- не равен глобальному `admin` SmartOil;
- получает доступ к `/mobile-sampling` и `/mobile-lab`, чтобы на старте франчайзи мог один отбирать пробу, анализировать и вводить результаты;
- включает права лаборанта в своей области данных;
- управление пользователями франчайзи должно выполняться через отдельную backend-функцию scoped-приглашений, а не через прямой `User.list/update`.

### Лаборант (`lab_technician`)

- привязан к одному `client_id`;
- вводит лабораторные результаты только по пробам своего клиента;
- может создать входящую пробу без QR из `/mobile-lab`;
- не управляет пользователями, активами и глобальными справочниками.

### Суперинтендант (`superintendent`)

- привязан к одному `client_id`;
- видит все активы и агрегаты своего клиента;
- работает с пробами, анализами, обслуживанием, графиками и отчетами;
- в отраслевом интерфейсе может называться главным механиком или главным инженером, но техническая роль остается одной.

### Ответственный за активы (`captain`)

`captain` - техническое имя роли, а не обязательное название должности.

- назначается на один или несколько активов;
- область задается массивом `asset_ids`;
- `asset_id` сохраняется как primary/legacy-поле для обратной совместимости;
- видит только назначенные активы и связанные агрегаты;
- отображаемая должность задается `position_title`.

Допустимые должности включают капитана, главного инженера, главного механика, механика, начальника цеха, мастера участка, оператора, машиниста экскаватора, водителя и нейтрального ответственного.

## Поля User

| Поле | Назначение |
|---|---|
| `role` | `admin`, `client_admin`, `lab_technician`, `superintendent`, `captain` |
| `client_id` | клиент администратора франчайзи, лаборанта, суперинтенданта или ответственного |
| `asset_id` | основной актив для совместимости |
| `asset_ids` | полный список назначенных активов |
| `position_title` | отображаемая должность |

Frontend-хук `useRoleAccess()` объединяет `asset_id` и `asset_ids` в уникальный `assignedAssetIds`.

## Назначение пользователя

1. Администратор приглашает пользователя по email.
2. После регистрации администратор задает роль и область.
3. Для `client_admin`, `lab_technician` и `superintendent` обязателен `client_id`.
4. Для `captain` выбираются один или несколько активов из списка и должность из справочника.
5. Пользователь входит отдельной тестовой учетной записью для проверки фактического RLS.

Переключатель "Просмотр как" в админском UI проверяет внешний вид и фильтрацию интерфейса, но не доказывает RLS. Настоящая проверка безопасности выполняется входом под соответствующим пользователем.

## Ожидаемая область данных

| Роль | Клиенты | Активы | Рабочие данные |
|---|---|---|---|
| admin | все | все | все |
| client_admin | свой клиент | все активы клиента | данные клиента, мобильные события и лабораторный ввод |
| lab_technician | свой клиент | все активы клиента для выбора пробы | ввод и чтение проб/анализов клиента |
| superintendent | свой клиент | все активы клиента | данные клиента |
| captain | связанный клиент | назначенные `asset_ids` | данные назначенных активов |

## Безопасность

- RLS уже присутствует в схемах сущностей.
- Backend-функции обязаны повторно проверять роль, `client_id` и разрешенные активы до `asServiceRole`.
- Update проверяет доступ к существующей записи и новому целевому контексту.
- UI-фильтрация не является защитой.
- Base44 JSON-RLS не поддерживает простой надежный оператор принадлежности `data.asset_id IN user.asset_ids`.

Из-за последнего ограничения часть схем пока использует только `user.asset_id`. Это известный риск `KI-001` в `src/docs/known-issues.md`; нельзя считать multi-asset безопасность полностью закрытой только по работе интерфейса.

## Проверка роли

Минимальная ручная приемка:

1. Войти отдельным администратором и убедиться в полном доступе.
2. Войти суперинтендантом и проверить, что чужой `client_id` недоступен прямым URL и запросом.
3. Войти ответственным с одним активом.
4. Войти ответственным с несколькими `asset_ids`.
5. Проверить read/create/update/delete для проб и событий.
6. Проверить, что прямой ID чужой записи возвращает отказ, а не только скрывается в меню.
