# Engineering Practices

Накопительная память проекта: проверенные решения, ограничения платформы и подходы, которые не следует повторять.

## Проверенные практики

### Формы Base44

- Перед create/update собирать whitelist payload через `buildPayload`.
- Никогда не отправлять полученный из Base44 объект целиком: системные поля могут привести к тихому отказу обновления.
- Ошибки сохранения обязательно показывать через `useSaveMutation.errorBlock`.
- Для составной формы родитель сохраняет основную сущность, затем вызывает `saveAll()` дочернего редактора.

### Источники истины

- Моточасы и текущее масло: `MaintenanceEvent -> EquipmentUnit.current_*`.
- Один `EquipmentUnit` является единственным местом отбора; отдельной сущности SamplingPoint нет.
- QR и способ отбора хранятся непосредственно в EquipmentUnit.
- Проба хранит снимок состояния на момент отбора.
- Пороги: индивидуальные пороги агрегата, затем стандартные правила выбранного масла.
- Наличие лабораторных данных определяется существованием `AnalysisResult`, а не наличием расчётного OHI. OHI может отсутствовать при уже заполненных измерениях.

### Диагностические индикаторы

- Зоны полукруглого индикатора нормализуются в диапазон 0..1 до построения SVG.
- Для дуги верхней полуокружности SVG-флаг большой дуги всегда равен 0: даже вся шкала занимает только 180 градусов.
- Вложенные диапазоны рисуются от широкого к узкому; цвет значения выбирается по самому узкому совпавшему диапазону.

### Backend и безопасность

- Любой вызов `asServiceRole` предваряется проверкой пользователя и доступности client_id/asset_id.
- Для роли ответственного проверяется весь массив `user.asset_ids`, а `user.asset_id` используется только как обратная совместимость.
- Update проверяет доступ и к существующей записи, и к новому целевому объекту.
- После изменения MaintenanceEvent пересчитываются обе стороны, если событие перенесено на другой агрегат.

### Живая проверка Base44

- OAuth-плагин Codex и Base44 CLI имеют независимые сессии. Исправная CLI-авторизация не обновляет истёкший токен плагина.
- Надёжный резервный канал: Base44 CLI + Deno + `base44 exec`.
- На Windows при `EPERM` системного npm-кэша использовать `--cache .npm-cache`.
- Перед production-запросом проверять `base44 whoami` и `base44/.app.jsonc`.
- Диагностику начинать с read-only операций. Запись и удаление требуют отдельного явного разрешения.
- После переподключения OAuth-плагина может потребоваться новый поток Codex, поскольку старый поток сохраняет прежний контекст инструментов.
- Полный runbook: `src/docs/base44-live-access.md`.

### Русский текст

- Файлы читаются как UTF-8.
- Якорь для патча берётся только из фактического содержимого файла.
- После изменения UI-текста выполняется поиск старого текста по репозиторию.

### Завершение задачи

- Обновить `ROADMAP.md`, если изменился продуктовый статус или риск.
- Дополнить этот файл, если найден новый устойчивый паттерн или тупиковый путь.
- Запустить `npm run build` и `npm run lint`.
- Коммит должен описывать одну законченную веху.

## Не повторять

### Shared-модули backend-функций

Base44 деплоит функции изолированно. Локальные shared-импорты между serverless-функциями не считаются надёжным вариантом для этого проекта.

### Function-to-function без проверки

Поддержка зависит от контекста и прав. До рефакторинга критической логики требуется acceptance-проверка для admin, superintendent и captain. Не заменять рабочую встроенную логику пересчёта предположением о передаче токена.

### Точечный lifecycle update

Закрытие одной активной записи и создание новой недостаточно при редактировании, удалении или задней дате события. Надёжный подход: хронологическая пересборка lifecycle и повторная привязка проб по окнам дат.

### Возврат SamplingPoint

Не добавлять промежуточную сущность между агрегатом и пробой без нового продуктового требования. В текущей модели один агрегат имеет одно место отбора, поэтому `OilSample`, `SamplingSchedule`, `MaintenanceEvent` и `OilLifecycle` ссылаются прямо на `equipment_unit_id`.

### Фильтрация только в UI

UI-фильтр не является защитой данных. RLS/backend определяет доступ, а UI повторяет ту же область данных для корректных KPI и интерфейса.

### Состояние проекта только в переписке

Архитектурные решения, риски и следующие шаги должны быть зафиксированы в репозитории. Переписка не является реестром проекта.

### Единственный канал доступа к Base44

Не полагаться только на OAuth-плагин или только на CLI. Для эксплуатационной приёмки поддерживать оба канала, чтобы истёкший токен одного из них не блокировал проверку.
