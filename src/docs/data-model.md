# Модель данных SmartOil

## Главная иерархия

```text
Client
  -> Asset
      -> EquipmentUnit
          -> OilSample
              -> AnalysisResult
          -> MaintenanceEvent
          -> OilLifecycle
          -> MaintenanceSchedule
          -> SamplingSchedule
```

Один `EquipmentUnit` является одним местом отбора. `SamplingPoint` удален из рабочей схемы.

## Реестр сущностей

| Сущность | Назначение | Основные связи |
|---|---|---|
| `Client` | организация-клиент | родитель `Asset` |
| `Asset` | судно, машина, площадка или иной объект | `client_id` |
| `EquipmentUnit` | контролируемый агрегат | `client_id`, `asset_id`, масло, QR, способ отбора |
| `OilReference` | справочник масел и паспортные данные | используется агрегатами, пробами и правилами |
| `ThresholdRule` | стандартные границы параметра для масла | `oil_type_id`, `parameter_name` |
| `OilSample` | проба и контекст отбора/приемки | клиент, актив, агрегат, масло, lifecycle |
| `AnalysisResult` | лабораторные измерения пробы | `sample_id` и денормализованный контекст |
| `MaintenanceEvent` | журнал моточасов, замен и доливов | `equipment_unit_id` |
| `OilLifecycle` | период работы масла между заменами | `equipment_unit_id`, масло, даты |
| `MaintenanceSchedule` | план обслуживания и замены | агрегат и плановые показатели |
| `SamplingSchedule` | график отбора проб | агрегат, стадии и следующая дата/наработка |
| `User` | роль и область доступа | `client_id`, `asset_id`, `asset_ids` |

## Денормализация

`client_id` и `asset_id` повторяются в нескольких сущностях намеренно:

- Base44 RLS надежнее работает с прямыми полями, чем с цепочками JOIN;
- списки и dashboards фильтруются без дополнительных запросов;
- backend обязан заполнять контекст из родительской записи, а не доверять произвольному значению фронта.

Перенос записи между клиентами или активами требует проверки старого и нового контекста.

## Snapshot-поля

Snapshot хранит состояние в конкретный момент и не должен восприниматься как первичный журнал:

- `EquipmentUnit.current_total_hours`;
- `EquipmentUnit.current_oil_hours`;
- `EquipmentUnit.current_oil_type_id`;
- `OilSample.total_hours_at_sampling`;
- `OilSample.oil_hours_at_sampling`;
- `OilSample.oil_type_id`.

Первые три пересчитываются из событий. Поля пробы сохраняются как исторический снимок и не должны меняться вслед за текущим агрегатом.

## Поля с особым статусом

### Legacy в схеме ThresholdRule

Схема сохраняет `client_id`, `asset_id`, `equipment_unit_id` и `equipment_type`, но текущая продуктовая логика стандартного правила использует:

- обязательный `oil_type_id`;
- `parameter_name`;
- глобальную область оборудования (`equipment_type = all`);
- индивидуальные правила хранятся в `EquipmentUnit.custom_thresholds`.

Удаление legacy-полей требует отдельной миграции и не выполняется автоматически.

### Скрытые поля OilReference

Семь паспортных полей остаются в схеме ради совместимости, но скрыты из UI и whitelist. Полный список и причина находятся в `AGENTS.md`.

### SamplingPoint

Сущности нет в репозитории. В удаленной базе могут оставаться старые записи; они не являются источником данных и подлежат отдельной контролируемой очистке.

## RLS и роли

| Роль | Область |
|---|---|
| `admin` | все данные |
| `superintendent` | записи своего `client_id` |
| `captain` | назначенные активы из `asset_ids`; `asset_id` сохраняется для совместимости |

Не все текущие JSON-RLS умеют проверять массив `asset_ids`; это активный риск, описанный в `known-issues.md`.

## Изменение схем

При добавлении или удалении поля нужно проверить:

1. JSONC-схему;
2. RLS;
3. whitelist в `src/utils/entityFields.js`;
4. формы create/update;
5. backend-функции;
6. dashboards, отчеты и экспорт;
7. миграцию существующих данных;
8. этот документ.
