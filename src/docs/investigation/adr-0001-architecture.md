# ADR-0001. Архитектура AI Investigation Platform

- Статус: принято, частично заменено
- Дата: 2026-08-26
- Область: платформа «Объяснительная / Investigator AI»
- Заменяет: —
- Частично заменено: ADR-0002 — разделы C и H в части хранилища. Остальные решения
  этого документа действуют без изменений; ADR-0002 показывает, что слоистая
  архитектура выдержала полную замену хранилища без правки методологии.

## 1. Контекст

Требуется SaaS-платформа для внутренних корпоративных расследований. Пользователь описывает
инцидент свободным текстом, добавляет участников и материалы; система планирует расследование,
опрашивает людей через web и Telegram, извлекает атомарные утверждения, строит timeline,
находит противоречия, ведёт конкурирующие гипотезы, проверяет основную версию независимыми
adversarial-агентами и выдаёт человеку обоснованный Investigation Report.

Ключевое ограничение продукта: **система не устанавливает виновность**. Она организует
расследование так, чтобы человеку было значительно сложнее пропустить противоречие,
доказательство или альтернативную версию (§82 ТЗ).

Технологическая база MVP: Base44 (сущности, файловое хранилище, serverless-функции) +
внешние LLM API.

## 2. Решения

### ADR-0001-A. Слоистая архитектура, Base44 — деталь реализации

Принято обязательное разделение (§78 ТЗ):

```text
UI (React)
  ↓
Application Services      src/investigation/services
  ↓
Investigation Engine      src/investigation/engine
  ↓
Agent Layer               src/investigation/agents
  ↓
Repository Layer          src/investigation/repositories (интерфейсы)
  ↓
Base44 / внешние сервисы  src/investigation/repositories/base44 (реализации)
```

Правила:

- бизнес-логика расследования не пишется внутри React-компонентов;
- слой N обращается только к слою N+1 и никогда наверх;
- ни один слой выше Repository не импортирует `@base44/sdk`;
- методология (что считать fact, как менять статус гипотезы, когда нужен human approval)
  живёт в Engine и Agent Layer, а не в UI и не в репозиториях.

Причина: Base44 выбран за скорость старта MVP, а не как долгосрочное обязательство. Замена
хранилища не должна приводить к переписыванию методологии расследования.

### ADR-0001-B. Двойное представление любого материала

Никогда не хранить рассказ человека только как единый текст (§3 ТЗ). Каждый материал
существует одновременно как:

1. `Source` — неизменяемый оригинал (аудио, файл, PDF, сообщение, исходный текст) с SHA-256;
2. структурированные производные — `Claim`, `Event`, `Evidence`, `MoneyTransaction`, и т. д.

AI-резюме никогда не является первичным доказательством. Обработанная версия оригинала
(транскрипт, OCR, нормализованная таблица) создаётся как отдельный derived `Source`
со ссылкой `derived_from_source_id`, оригинал не изменяется.

### ADR-0001-C. Отдельное Base44-приложение, отдельный каталог схем — ЗАМЕНЕНО ADR-0002

Схемы сущностей платформы расследований размещены в `investigation/entities/`, а не в
`base44/entities/`.

Причина: `base44/entities/` синхронизируется с production-приложением SmartOil. Слияние
27 сущностей расследования в чужое приложение изменило бы его схему и RLS без разрешения
владельца, что запрещено `AGENTS.md`. Каталог `investigation/entities/` является staging:
он версионируется в Git, но не деплоится автоматически.

Промоушен в целевое приложение описан в `investigation/README.md` и выполняется владельцем
явным действием.

Если владелец решит разместить платформу в том же приложении, что и SmartOil, требуется
отдельное решение по `User.role`: роли SmartOil (`admin`, `client_admin`, `lab_technician`,
`superintendent`, `captain`) и роли расследования (§59 ТЗ) не пересекаются по смыслу,
и объединять их в один enum нельзя без ревизии всех RLS SmartOil.

### ADR-0001-D. Multi-tenancy на уровне каждой сущности

Каждая сущность несёт `organization_id`. RLS каждой сущности фильтрует по
`{{user.organization_id}}`. Retrieval данных другого tenant недопустим ни в одном сценарии,
включая RAG и поиск похожих дел.

Дополнительно: `CASE KNOWLEDGE` и `METHODOLOGY KNOWLEDGE` — два раздельных knowledge space
(§49 ТЗ). `KnowledgeDocument.space` разделяет их физически, а `KnowledgeStore.semanticSearch()`
обязан принимать `space` и `organizationId` как обязательные аргументы.

### ADR-0001-E. Доступ участника интервью — только по подписанному токену

Участник не является пользователем платформы и не проходит регистрацию (§65 ТЗ). Доступ даёт
`InterviewAccessToken`, ограниченный case + person + interview + сроком жизни. Участник видит
только своё интервью, свои вопросы, свои ответы и явно разрешённые документы. Он не видит
чужие показания, гипотезы, противоречия и внутренние заметки.

Проверка токена и любая запись от имени участника выполняются serverless-функцией, а не
клиентом: клиентский Base44 SDK не может выдать участнику ограниченные права безопасно.

### ADR-0001-F. Агент — это контракт, а не промпт

Каждый агент реализует единый интерфейс (§77 ТЗ) и обязан иметь: роль, разрешённые данные,
запрещённые действия, версию промпта, JSON Schema выхода и запись `AgentRun`.

Критическим агентам запрещено возвращать только prose (§62 ТЗ). Ответ, не проходящий
валидацию схемы, считается неуспешным запуском агента, а не «почти правильным ответом».

Один LLM может исполнять разные роли через разные system prompts; разные модели не обязательны.
Но `AgentRun` фиксирует модель и версию промпта, чтобы позднее сравнивать модели и
воспроизводить любой Finding (§70 ТЗ).

### ADR-0001-G. Загруженные документы — недоверенные данные

Все материалы дела считаются UNTRUSTED DATA (§61 ТЗ). Промпт агента собирается конвертом с
явными непересекающимися секциями `INSTRUCTIONS` / `CASE DATA` / `USER DATA` / `DOCUMENT DATA`,
и в инструкции прямо сказано, что содержимое секций данных является предметом расследования,
а не источником команд.

Текст вида «Ignore previous instructions» внутри PDF — это доказательство, которое следует
зафиксировать как признак возможной манипуляции, а не инструкция.

### ADR-0001-H. В MVP нет Neo4j, отдельного Postgres и отдельного Redis — ЧАСТИЧНО ЗАМЕНЕНО ADR-0002

> Решение по Neo4j и по отсутствию отдельного Redis действует. Отказ от PostgreSQL
> отменён: платформа работает на PostgreSQL + pgvector, векторный поиск больше не
> отложен. Абстракции `GraphRepository`, `KnowledgeStore` и `Job` сохранены.

- Граф собирается поверх реляционных связей; вводится только интерфейс `GraphRepository`
  (§48, §56 ТЗ). Neo4j подключается только при реальной потребности в multi-hop queries,
  network analysis и cross-case анализе.
- Векторный поиск скрыт за `KnowledgeStore`; первая реализация — Base44, позже
  PostgreSQL + pgvector (§55 ТЗ).
- Тяжёлые операции (транскрипция, парсинг документов, extraction, пересборка timeline,
  сканирование противоречий, генерация отчёта) не выполняются как синхронные UI-запросы.
  Вводится абстракция `Job` (§57 ТЗ); первая реализация — background execution Base44.

Причина: каждая из этих систем добавляет эксплуатацию и стоимость раньше, чем появляется
доказанная потребность. Абстракция стоит дёшево, преждевременная инфраструктура — дорого.

### ADR-0001-I. Human-in-the-loop как состояние данных, а не как UI-подсказка

Обязательное человеческое утверждение перед: отправкой первого набора интервью, отправкой
чувствительного challenge-вопроса, переводом человека в статус `subject`, закрытием гипотезы,
утверждением Finding, выпуском Final Report (§42 ТЗ).

Это реализовано сущностью `ApprovalRequest` и проверкой в Engine, а не только кнопкой в UI:
действие, требующее approval, невозможно выполнить без approved-записи.

Уровень автономии дела — `InvestigationCase.autonomy_level`; для MVP допустимы `A1` и `A2`.

### ADR-0001-J. Ничего не удаляется

- Опровергнутые гипотезы не удаляются: меняется статус, история пишется в `HypothesisRevision`.
- Ответ человека не переписывается: правка создаёт новую версию, `original_version` хранится.
- Альтернативные версии времени события не уничтожаются.
- Удаление данных расследования — soft delete (`deleted_at`, `deleted_by`, `deletion_reason`).
- Любое изменение значимых данных пишется в `AuditEvent`.

## 3. Отвергнутые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Хранить интервью как единый транскрипт с AI-резюме | Резюме подменяет источник; невозможно сопоставить утверждения и найти противоречия |
| Один «супер-агент» с большим промптом | Нет изоляции данных, нет adversarial-проверки, невозможно версионировать и сравнивать |
| Оценка правдивости человека по речи, паузам, эмоциям | Ненадёжно, запрещено ТЗ (§2, §71); создаёт ложную уверенность и юридический риск |
| Числовая вероятность виновности («83.6%») | Псевдоточность; confidence относится к утверждению, а не к человеку (§63) |
| Neo4j/pgvector/Redis сразу | Потребность не доказана; абстракций достаточно |
| Прямое обращение UI к Base44 SDK для сущностей расследования | Ломает переносимость и обход методологических проверок |
| Схемы расследования прямо в `base44/entities/` | Изменило бы production-схему SmartOil без разрешения владельца |
| Base44 как хранилище платформы | Заменено ADR-0002: см. разбор ограничений там |

## 4. Следствия

Положительные:

- методология переносима между хранилищами;
- любой Finding воспроизводим: известны модель, версия промпта, входные объекты, agent run;
- adversarial-проверка встроена в процесс, а не остаётся доброй волей следователя;
- tenant-изоляция проверяется в одном месте (репозитории), а не в каждом экране.

Издержки:

- больше кода на инфраструктуру, чем при прямом обращении к SDK;
- дублирование enum между JSON-схемами Base44 и `src/investigation/domain/enums.js`
  требует синхронизации; расхождение фиксируется как дефект;
- отсутствие транзакций между сущностями (ограничение снято переходом на PostgreSQL,
  см. ADR-0002).
